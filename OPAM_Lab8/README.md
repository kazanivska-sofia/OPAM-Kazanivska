# Лабораторна робота №8. Алгоритми пошуку та їх порівняння

**Варіант:** N=11, K=22 (a=2, b=3, c=1)

---

## 1. Пояснення до Завдання 1
Третій запит (пошук відсутнього елемента зі значенням 101) виявився найдорожчим, тому що лінійний пошук змушений перебрати всі $N = 100\,000$ елементів масиву, перш ніж переконатися, що елемента немає ($O(N)$ порівнянь).

---

## 2. Прояв поломок Бінарного Пошуку (Завдання 2)

| № | Поломка | Прояв |
| :- | :--- | :--- |
| 1 | `while (lo < hi)` замість `<=` | Не знаходить елемент, якщо він знаходиться на останньому кроці, коли `lo == hi`. |
| 2 | `lo = mid` замість `mid + 1` | Нескінченне зациклення програми, межі перестають зсуватися. |
| 3 | `mid = (lo + hi) / 2` | Переповнення `int` при $lo + hi > 2\,147\,483\,647$, що призводить до від'ємного індексу та `IndexOutOfRangeException`. |
| 4 | Невідсортований масив | Більшість пошуків повертають `-1`, хоча елемент наявний у масиві. |

---

## 3. Відповідь на Завдання 3 (b = 3)
Кількість порівнянь під час пошуку межі не залежить від кількості елементів, що відповідають умові, оскільки бінарний пошук завжди робить рівно $\lceil \log_2 N \rceil$ кроків для звуження діапазону індексів до одного елемента.

---

## 4. Відповіді на питання (Завдання 6)

1. **Зміряне число точки окупності проти лекційного 34:**  
   Практична точка окупності за часом (мс) вища за теоретичну (близько 40–60 запитів), оскільки `Array.Sort` вимагає додаткових витрат пам'яті та кешу процесора.
2. **Питання про `HashSet` / `Dictionary`:**  
   - Чи потрібне нам збереження порядку елементів та можливість швидкого пошуку діапазону (Lower/Upper Bound)? (У хеш-таблицях пошук діапазону неможливий).  
   - Чи критичне споживання оперативної пам'яті? (Масив займає менше пам'яті, ніж хеш-таблиця).
3. **Вибір для даних, що надходять потоком:**  
   Якщо дані надходять потоком і масив постійно змінюється, сортування після кожного додавання коштуватиме $O(N \log N)$. У такому разі варто обрати **хеш-структуру (`HashSet` / `Dictionary`)** або збалансоване дерево пошуку.
